# Feasibility Constraints: Open, Lightweight Platform for Many Sandboxed GUI MicroVMs for AI Computer Use (MCP-controlled, live-monitored), as of November 2026

Research date: 2026-11-27. All prices are list prices seen on or near that date unless noted. Items marked (secondary) come from third-party sites, not the vendor. Items marked (possibly outdated) were not re-verified against a 2026 primary source.

## 1. KVM / nested virtualization availability, host OS support, and non-KVM fallbacks

### Takeaway
KVM is now available on many more cloud VMs than a year ago (AWS added nested virtualization on regular instances in Feb 2026, expanded in Jun 2026; GCP and Azure have had it for years), but every nested option carries a performance tax and restrictions, so bare metal (AWS .metal, Hetzner, OVH) remains the "serious" host for dense microVM fleets. macOS and Windows hosts cannot run Firecracker at all; they need a different hypervisor backend per OS, and without hardware virtualization the fallbacks (QEMU TCG, gVisor) are either roughly 8x to 12x slower or are not real VMs.

### Cited Findings
**AWS**
- 2026-02-16: AWS launched nested virtualization on virtual (non-metal) EC2 instances, initially C8i, M8i and R8i in all commercial regions; customers can run KVM or Hyper-V inside them. Before this, nested VMs on EC2 required bare metal instances. [AWS What's New, Feb 2026](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-ec2-nested-virtualization-on-virtual)
- 2026-06-18: expanded to C7i, R7i, M7i, C8id, R8id, M8id, several flex variants, I7i and X8i, plus both AWS GovCloud (US) regions. No AMD or Graviton families surfaced in announcements. [AWS What's New, Jun 2026](https://aws.amazon.com/about-aws/whats-new/2026/06/nested-virtualization-intel-us-gov-cloud/)
- It is enabled through an API option at launch, and AWS still recommends bare metal for workloads highly sensitive to performance or latency. [InfoQ, Mar 2026](https://www.infoq.com/news/2026/03/aws-ec2-nested-virtualization/); [The Register, Feb 2026](https://www.theregister.com/2026/02/17/nested_virtualization_aws_ec2/)
- Bare metal reference price: c7i.metal-48xl (192 vCPU, 384 GiB, 50 Gbps) is $8.568/hour on-demand in us-east-1 (about $6,254/month); spot about $2.239/hour. (secondary, consistent across three trackers) [Vantage](https://instances.vantage.sh/aws/ec2/c7i.metal-48xl); [Holori](https://calculator.holori.com/aws/ec2/c7i.metal-48xl); [Economize, updated 2026-07-09](https://www.economize.cloud/resources/aws/pricing/ec2/c7i.metal-48xl/)

**Google Cloud**
- Nested virtualization works by exposing VT-x/AMD-V to the L1 VM. Restrictions: E2 VMs and Arm VMs unsupported; for AMD only N4D is supported; memory-optimized VMs excluded except M4/M4N. The only supported L1 hypervisor is Linux KVM (Hyper-V not supported, so WSL2 does not work on Windows VMs). Licensed L2 OSes must be bring-your-own-license. Google states nested VMs "might experience a 10% or greater decrease in performance for workloads that are CPU-bound", and I/O-bound workloads may see more than 10%. [GCP nested virtualization overview](https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview)
- Firecracker's own dev-setup doc recommends a GCE VM for development because it supports nested virtualization; its Azure section was an empty TODO. (possibly outdated mirror) [Firecracker dev machine setup (mirror)](https://cocalc.com/github/aos/firecracker/blob/main/docs/dev-machine-setup.md)

**Azure**
- Dv5/Dsv5 spec pages list "Nested Virtualization: Supported". [Microsoft azure-docs, Dv5/Dsv5](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/virtual-machines/dv5-dsv5-series.md)
- B-series and A-series do not support nested virtualization; check /proc/cpuinfo for vmx/svm. (secondary) [OneUptime, 2026-02-16](https://oneuptime.com/blog/post/2026-02-16-how-to-enable-nested-virtualization-on-an-azure-virtual-machine/view)
- Microsoft does not test non-Microsoft hypervisors running on Hyper-V and tells users to check with the hypervisor vendor. [Microsoft Learn, Hyper-V nested virtualization](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization)
- A forum report says QEMU 10.2 added an MSHV accelerator so Linux guests can avoid nested-virtualization overhead on Hyper-V, but only on Azure or Hyper-V root-partition hardware. (anecdotal) [Proxmox forum](https://forum.proxmox.com/posts/846733/)

**DigitalOcean and others**
- DigitalOcean "doesn't officially support nested virtualization"; it sometimes works on Intel hosts, reportedly not on AMD (2022 feature request), with poor performance warnings. (community answers, no official doc found) [DO community Q&A](https://www.digitalocean.com/community/questions/does-digitalocean-support-kvm-or-nested-virtulzation); [DO ideas: enable nested KVM on AMD](https://ideas.digitalocean.com/core-compute-platform/p/enable-nested-kvm-in-amd-servers)
- Running Firecracker in an OCI VM requires nested virtualization so /dev/kvm exists in the guest. [Oracle Cloud Infrastructure blog](https://blogs.oracle.com/cloud-infrastructure/?p=13060)

**Hetzner (bare metal)**
- Hetzner raised prices three times in 2026. From 2026-04-01 (applied to existing customers too): cloud +30% to 37% in DE/FI, dedicated +3% to 21%. Examples: AX162-R (high-RAM) EUR 207.30 to EUR 242.30/month (+17%); AX102 EUR 107.30 to EUR 122.30; CCX63 (32 dedicated vCPU / 128 GB) EUR 287.99 to EUR 374.49. A 2026-06-15 restructure (new orders only) moved dedicated lines to -1/-2/-3 configs and removed custom RAM/storage options. Hetzner cited RAM and NVMe SSD cost increases; the article cites TrendForce server DRAM contract prices +43% to 48% in Q4 2025, with further projected rises in 2026. [webhosting.today, 2026-05-29](https://webhosting.today/2026/05/29/hetzner-has-now-raised-prices-three-times-in-2026-this-one-is-different/); [DatacenterDynamics](https://www.datacenterdynamics.com/en/news/german-cloud-firm-hetzner-hikes-prices-by-up-to-50-percent-due-to-drastic-component-price-increases); [Tom's Hardware](https://www.tomshardware.com/tech-industry/hetzner-to-raise-prices-by-up-to-37-percent-from-april-1)
- Conflict: Hetzner's official price-adjustment table (snippet only, page 404'd on fetch) lists an "AX162-1" going 612.30 to 722.10 with setup 304.00 to 359.00, which does not match the AX162-R figure above; likely a different configuration after the June rename. [Hetzner Docs, price adjustment](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/)

**macOS hosts**
- Apple's Virtualization.framework enforces the 2-VM cap only for macOS guests (VZMacPlatformConfiguration) and has no fixed cap for Linux guests (VZGenericPlatformConfiguration); Apple DTS says two Mac VMs plus any number of Linux VMs via Containerization should work (Sep 2026). [Apple Developer Forums thread 845455](https://developer.apple.com/forums/thread/845455)
- Nested virtualization (KVM inside the guest) on Apple silicon requires an M3 or newer host and macOS 15+, and is exposed only on VZGenericPlatformConfiguration (Linux guests); macOS guests never get it. Arm64 nested virtualization support in the Linux kernel itself landed in 6.16. (mix of DTS and forum sources) [Apple Developer Forums thread 827663](https://developer.apple.com/forums/thread/827663); [UTM issue 6700](https://github.com/utmapp/UTM/issues/6700); [LWN](https://lwn.net/Articles/1038896)
- OSWorld notes macOS hosts generally do not support KVM and recommends VMware there. [OSWorld README](https://github.com/xlang-ai/OSWorld)

**Windows hosts**
- Hyper-V supports nesting with per-VM opt-in; WSL2 inside a nested Hyper-V VM is listed as supported, and users enable nested virtualization in WSL2 through .wslconfig, with reports of it failing where Hyper-V works. [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/nested-virtualization); [WSL issue 11216](https://github.com/microsoft/WSL/issues/11216)

**Fallbacks without KVM**
- QEMU TCG: Linaro measured Android boot at 8x slower for an x86-64 guest and 12x slower for an aarch64 guest vs. hardware acceleration; a QEMU developer's 2018 rule of thumb is about 12x slower for integer workloads. (possibly outdated) [Linaro blog](https://www.linaro.org/blog/qemu-a-tale-of-performance-analysis/); [Launchpad bug 1529173](https://bugs.launchpad.net/qemu/+bug/1529173/comments/2)
- gVisor: KVM platform is fastest on bare metal; Systrap is recommended inside a VM or without virtualization support and often performs better under nested virtualization; largest overheads are networking and file I/O. A 2021 measurement showed getpid at 62 ns native, 830 ns runsc-KVM, 6,249 ns runsc-ptrace (pre-Systrap, outdated). [gVisor platform guide](https://gvisor.dev/docs/architecture_guide/platforms); [gVisor performance guide](https://gvisor.dev/docs/architecture_guide/performance/); [gVisor Systrap release](https://gvisor.dev/blog/2023/04/28/systrap-release/)
- Running Firecracker without KVM on regular cloud VMs is a known pain point that drove workarounds. [Alex Ellis blog](https://blog.alexellis.io/how-to-run-firecracker-without-kvm-on-regular-cloud-vms/)

### Inferences
- "Use whatever virtualization is available" means at least three backends: Firecracker or Cloud Hypervisor on Linux/KVM, Virtualization.framework on macOS (Linux guests only, macOS guests capped at 2), and Hyper-V/WSL2 or QEMU+WHPX on Windows. Each backend has a different device model, snapshot format and networking stack, so "one lightweight platform" is really three integration surfaces.
- For a hosted fleet, AWS nested virt on C8i/M8i/R8i is useful for development and small deployments, but density math should assume bare metal because nested virt adds at least about 10% CPU overhead (GCP's stated figure) plus extra I/O penalty, and AWS itself steers latency-sensitive users to metal.
- The 2026 DRAM price spike directly hits this product, because RAM (not CPU) is the binding constraint for GUI desktops (see section 4). Self-hosted bare metal price advantages narrowed in 2026.
- A no-KVM fallback (TCG) is fine for a demo but not for interactive desktops: an 8x to 12x CPU slowdown turns a 2-vCPU Chromium desktop into something unusable. gVisor is not a VM and does not run a full desktop OS kernel, so it is a container-grade fallback, not a microVM equivalent.

### Gaps
- No primary benchmark found for Firecracker running on AWS nested virtualization (C8i etc.) vs. .metal; Firecracker's official stance on supporting nested hosts in production was not verified.
- Azure did not publish a single authoritative list of nested-capable sizes in results; only per-series pages.
- GCP does not state any extra charge for nested virtualization; none was found, but absence was not confirmed.
- Hetzner AX162-R exact CPU/RAM spec and post-June-2026 price for new orders were not confirmed from a primary source.

## 2. OS licensing: macOS, Windows, Android

### Takeaway
Linux desktops are the only license-clean option for a multi-tenant hosted fleet. macOS is legally limited to 2 extra VMs per Apple-branded Mac, for development/testing/personal use, with service-bureau style use excluded and a 24-hour minimum lease for hosted developer services. Windows 11 cannot be resold as a hosted desktop via SPLA; it requires the customer to bring qualifying per-user Enterprise/VDA licenses to Azure or an authorized/qualified hoster, while the SPLA route is Windows Server with RDS. Android (AOSP emulator, Cuttlefish) is license-friendly but needs KVM.

### Cited Findings
**macOS**
- macOS 27 EULA (as quoted Sep 2026): "except as otherwise provided in writing, signed, or issued by an authorized representative of Apple, to install, use and run up to two (2) additional copies or instances ... within virtual operating system environments on each Apple-branded computer you own or control that is already running the Apple Software, for purposes of: (a) software development; (b) testing during software development; (c) using macOS Server; or (d) personal, non-commercial use." A developer asking how to obtain a written exception got no path from Apple DTS or support. [Apple Developer Forums thread 845455](https://developer.apple.com/forums/thread/845455)
- Older macOS SLAs state the virtualization grant "does not permit you to use the virtualized copies or instances of the Apple Software in connection with service bureau, time-sharing, terminal sharing or other similar types of services." (older text; current wording not fetched) [Apple macOS 10.7.2 SLA PDF](https://www.apple.com/legal/sla/docs/macosx1072.pdf)
- Since macOS Big Sur, a "Leasing for Permitted Developer Services" section allows leasing a Mac and its software in its entirety to an individual or organization "for a minimum period of twenty-four (24) consecutive hours", including running additional virtual copies during the lease. [9to5Mac, 2020-11-11](https://9to5mac.com/2020/11/11/macos-big-sur-adds-leasing-terms-that-pull-hosting-services-like-macstadium-out-of-a-legal-gray-area/)
- An analysis of Mac DaaS concludes Apple permits developers to lease macOS from providers but prohibits DaaS for end users, and macOS must run on Apple hardware. [TechTarget](https://www.techtarget.com/enterprise-software/tip/Understanding-the-DaaS-options-for-Macs?amp=1)
- AWS EC2 Mac: per-second billing but a 24-hour minimum Dedicated Host allocation "to comply with Apple's macOS license"; one Mac instance per host; mac2-m2.metal (8 vCPU, 24 GiB) about $0.878/hour in us-east-1, so about $21 minimum per host allocation. (price is secondary) [AWS EC2 Mac FAQ](https://aws.amazon.com/ec2/instance-types/mac/faqs/); [Classmethod pricing API write-up](https://dev.classmethod.jp/en/articles/ec2-mac-m3ultra-metal-pricing-api/)
- Developers on Apple's forums are actively asking how to build scalable macOS CI under the 2-VM limit on high-end hardware, indicating no sanctioned bypass. [Apple Developer Forums thread 830383](https://developer.apple.com/forums/thread/830383)

**Windows**
- Running/accessing a Windows 11 VM requires one of: Windows 11 Enterprise E3/E5, Education A3/A5, Microsoft 365 F3/E3/E5/E7 or A3/A5, Microsoft 365 Business Premium, Windows VDA E3/E5, Windows VDA per device, or Windows 11 Enterprise per device with SA. OEM licenses typically lack virtualization rights. Per-device licenses are not eligible for Azure Virtual Desktop. Each eligible user may access up to four VMs on on-prem or Authorized Outsourcer servers; on "Listed Providers" only Windows VDA E3/E5 confers rights, and only on servers dedicated to that customer. [Microsoft, Windows 11 Licensing for Virtual Desktops](https://www.microsoft.com/licensing/guidance/Windows-11-Licensing-for-Virtual-Desktops)
- Multitenant Hosting Rights for Windows 11 apply to customers with Windows 11 Enterprise E3/E5 per user or AVD Access per user, letting them bring licenses to a hoster's environment. [Microsoft Learn, Windows desktop multitenant hosting](https://learn.microsoft.com/en-us/azure/virtual-machines/windows/windows-desktop-multitenant-hosting-deployment)
- Community and licensing-blog sources state SPLA does not cover Windows client desktops; a hoster can run Windows 11 only as a Qualified Multitenant Hoster with customer-owned licenses, and SPLA's route is Windows Server + RDS. (not confirmed in Microsoft Product Terms in this research) [Microsoft Q&A](https://learn.microsoft.com/en-sg/answers/questions/2117477/windows-server-os-based-vdi-with-spla); [o365hq licensing blog](https://o365hq.com/blog/every-way-to-run-windows-as-a-virtual-machine-licensing-channels-pros-cons-and-cost); [Zettagrid QMTH](https://www.zettagrid.com/qualified-multitenant-hoster-program)
- Windows 365 Cloud PCs must each be assigned to a specific user. [Microsoft licensing guidance](https://www.microsoft.com/licensing/guidance/Windows-11-Licensing-for-Virtual-Desktops)
- GCP requires bring-your-own-license for licensed OSes in nested L2 VMs. [GCP nested virtualization overview](https://docs.cloud.google.com/compute/docs/instances/nested-virtualization/overview)
- Market signal: Cua offered cloud Windows sandboxes (Small 2 cores/8 GB, Medium 4/16, Large 8/32 at 8/15/31 credits per hour) and macOS on bare-metal M1/M2/M4 hosts, but "Cua Cloud (Fleets) ended on 18 October 2026"; no reason given. [Cua blog, updated note](https://cua.ai/blog/cloud-windows-ga-macos-preview)

**Android**
- The x86_64 Android Emulator is "much faster with KVM"; Google recommends nested virtualization on cloud machines and `-no-window` for headless. Without KVM it falls back to very slow ARM emulation. [AOSP Virtualization docs (goldfish)](https://android.googlesource.com/platform/packages/modules/Virtualization/+/170553f5/docs/getting_started/goldfish.md); [community gist, 2021](https://gist.github.com/WestonThayer/75a5098c8d38cb51a3a44ffe55a1e23c)
- Cuttlefish also requires KVM and is headless by design (access via adb or remote desktop/WebRTC). [AOSP Cuttlefish README](https://android.googlesource.com/device/google/cuttlefish/+show/refs/heads/android15-tests-dev/README.md); [Build your own cloud emulator](https://source.android.com/docs/automotive/start/avd/cloud_emulator)

### Inferences
- A public, multi-tenant "spin up a macOS desktop for an agent" service is effectively ruled out legally (2 VMs per Mac, development/testing purposes, no service-bureau use, 24-hour minimum lease). At best, a self-hosted mode on the user's own Mac (2 macOS VMs max) is viable.
- Windows is possible only as bring-your-own-license or via Windows Server + RDS SALs under SPLA. Hosted Windows 11 for anonymous users is not a clean option. The fact that Cua shut its hosted Windows/macOS fleet in Oct 2026 is a signal (cause unknown) that this segment is hard to operate.
- Scope recommendation: Linux (Ubuntu/Debian + XFCE or similar) as the only first-class hosted desktop; Android via Cuttlefish/emulator as a second target on bare-metal KVM hosts; Windows and macOS as "bring your own host/license" adapters.

### Gaps
- Current (macOS 26/27) full SLA text for the service-bureau clause and the leasing section was not fetched; wording may have changed.
- Microsoft Product Terms text for SPLA exclusion of Windows client OS and the current Listed Providers list (aka.ms/ListedProviders) was not retrieved.
- Android emulator system image licensing for redistribution (Google Play images vs. AOSP) not researched.

## 3. Graphics in microVMs

### Takeaway
Firecracker has no display or GPU device and no path to one; Cloud Hypervisor upstream has no virtio-gpu either. Everyone (Anthropic's reference, E2B Desktop) runs a virtual X framebuffer (Xvfb) inside the guest plus VNC/noVNC, with all rendering on the CPU. A 2025-2026 Chromium change makes this worse: automatic SwiftShader WebGL fallback is deprecated, so WebGL context creation fails by default without a GPU unless you pass an "unsafe" flag.

### Cited Findings
- Firecracker GPU support is described in its issue tracker as very difficult with no known route. [Firecracker issue 849](https://github.com/firecracker-microvm/firecracker/issues/849)
- Firecracker added optional PCI transport (`--enable-pci`) and virtio-mem memory hotplug in v1.13.0, plus developer-preview PCI device hotplug (block, pmem, net); VFIO hotplug commits were visible in a May 2026 branch but release status is unconfirmed. [Firecracker CHANGELOG](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/CHANGELOG.md); [Firecracker device hotplug doc v1.16.1](https://raw.githubusercontent.com/firecracker-microvm/firecracker/v1.16.1/docs/device-hotplug.md)
- Cloud Hypervisor upstream lacks virtio-gpu; the Spectrum OS project maintains a patchset that uses crosvm's virtio-gpu over vhost-user (tested up to Cloud Hypervisor 50.0), and Cloud Hypervisor developers have shown little interest in GPU work. [Spectrum OS docs](https://inbox.spectrum-os.org/spectrum-devel/d746c82/s/Documentation-software-cloud-hypervisor-index.html)
- QEMU provides virtio-gpu (including virgl/venus variants). [QEMU virtio-gpu docs](https://www.qemu.org/docs/master/system/devices/virtio/virtio-gpu.html)
- Fly.io runs GPU machines on Cloud Hypervisor (not Firecracker) for passthrough. (secondary) [sysdesign wiki summary](https://sysdesign-wiki.pages.dev/systems/intel-cloud-hypervisor/)
- Anthropic's reference implementation: Docker container, Xvfb virtual X11 display, Mutter window manager, Tint2 panel, Firefox, LibreOffice. [Claude computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- E2B Desktop: startup script launches Xvfb, XFCE, a VNC server, and noVNC on port 6080; the sample uses 1024x768 at 24-bit. E2B gives every session a Firecracker microVM. [E2B desktop template docs](https://e2b.dev/docs/template/examples/desktop); [E2B Desktop README](https://raw.githubusercontent.com/e2b-dev/desktop/main/README.md)
- Chromium: automatic SwiftShader WebGL fallback is deprecated (deprecation period began in Chrome 130); WebGL context creation will fail instead of falling back. Opt-in requires `--use-gl=angle --use-angle=swiftshader-webgl --enable-unsafe-swiftshader`, described as accepting lower security guarantees and "not intended for running untrusted content". An EnableUnsafeSwiftShader enterprise policy exists (Windows since Chrome 139, labeled temporary). Chrome 139 began experiments removing SwiftShader on macOS/Linux; there were "no plans for a default software fallback on Linux". llvmpipe is blocked in Chromium's software_rendering_list (unlike Firefox). [Chromium SwiftShader doc](https://chromium.googlesource.com/chromium/src/+/798e59c5275d4131797e8ea2e96e6c6000256b58/docs/gpu/swiftshader.md); [blink-dev Intent to Remove: SwiftShader Fallback](https://groups.google.com/a/chromium.org/g/blink-dev/c/yhFguWS_3pM); [blink-dev thread on llvmpipe](https://mail-archive.com/blink-dev@chromium.org/msg14549.html)
- In software-only headless setups, accelerated video decode is disabled and decoding falls back to CPU. [Launchpad chrome://gpu output](https://bugs.launchpad.net/ubuntu/+source/chromium-browser/+bug/1899270/comments/4)

### Inferences
- The display stack must live inside the guest (Xvfb or a headless Wayland compositor) and frames must be exported over the network (VNC, WebRTC) or via an in-guest agent over vsock. There is no host-side framebuffer to grab with Firecracker, unlike QEMU's VNC display.
- WebGL-heavy sites (maps, dashboards, Figma-like apps, some captchas) will break by default in current Chromium inside GPU-less microVMs; enabling SwiftShader is possible but Chromium explicitly flags it as unsafe for untrusted content, which is exactly what agents browse. Firefox with llvmpipe may be the more compatible default browser for GPU-less desktops.
- Video playback and screen streaming both burn CPU with no hardware decode/encode in the guest; budget a substantial fraction of a core per desktop while video plays.
- If GPU-backed desktops become a requirement, the hypervisor choice shifts to QEMU or Cloud Hypervisor with passthrough/virtio-gpu, giving up some Firecracker density and simplicity.

### Gaps
- No measured CPU cost found for Chromium with SwiftShader/llvmpipe for typical agent browsing, WebGL, or 720p/1080p video playback on a 2-vCPU microVM.
- Final Chrome milestone that removed SwiftShader WebGL fallback on Linux was not confirmed.

## 4. Resource math and density

### Takeaway
A realistic agent desktop (Xvfb + light WM + Chromium + a couple of apps) needs about 2 vCPU and 2 to 4 GiB RAM; the reference configurations used in industry are larger (Cua Windows Small 2 cores/8 GB; OSWorld example 8 cores/8 GB). Because agents idle most of the time waiting on the model, CPU overcommits well but RAM does not, so RAM is the binding constraint. On a 64-core/256 GB host that is roughly 60 desktops at 4 GiB or about 120 at 2 GiB before memory overcommit. Overcommit techniques (balloon, virtio-mem, KSM, snapshot CoW) exist but add complexity and are the code paths where a November 2026 Firecracker CVE lives.

### Cited Findings
- Industry configs: Cua Windows sandboxes were Small 2 cores/8 GB/128 GB SSD, Medium 4/16, Large 8/32. [Cua blog](https://cua.ai/blog/cloud-windows-ga-macos-preview). OSWorld's Docker example starts its VM with RAM_SIZE=8G and CPU_CORES=8 and passes /dev/kvm. [OSWorld Docker provider docs](https://timothyxxx.github.io/OSWorld/installation/install_provider/docker.html). E2B's price calculator example uses 2 vCPU and 512 MiB (code sandbox, not desktop). [E2B pricing docs](https://e2b.dev/docs/pricing)
- Chromium memory: roughly 100 to 300 MB baseline plus 50 to 150 MB per open page, more for media-heavy sites; peak usage matters more than average; Docker's default 64 MB /dev/shm causes renderer crashes without `--disable-dev-shm-usage`. (secondary estimates, no Chrome official figure) [webscraping.ai FAQ](https://webscraping.ai/faq/headless-chromium/what-are-the-resource-requirements-for-running-headless-chromium-at-scale); [DEV: headless Chromium fleet eating RAM](https://dev.to/rendershot/headless-chromium-at-scale-four-fixes-for-a-fleet-that-kept-eating-ram-1mdp)
- Firecracker snapshots: loading maps the guest memory file privately so pages load on demand and writes go to a copy-on-write anonymous mapping; the design allows sharing memory pages and read-only disks between microVMs; the memory file must be kept for the lifetime of the resumed VM. [Firecracker snapshot support docs](https://github.com/firecracker-microvm/firecracker/blob/master/docs/snapshotting/snapshot-support.md)
- Snapshot restore of about 28 ms on a dev machine with per-VM CoW overlays for memory and rootfs (single-author blog). [DEV: sandboxes that boot in 28ms](https://dev.to/adwitiya/how-i-built-sandboxes-that-boot-in-28ms-using-firecracker-snapshots-i0k). E2B spins up a new sandbox in about 150 ms. [E2B blog: How Manus uses E2B, 2025-05](https://e2b.dev/blog/how-manus-uses-e2b-to-provide-agents-with-virtual-computers)
- Sabre (OSDI '24) speeds snapshot memory restoration by up to 55% via prefetching. [Sabre paper](https://www.csl.cornell.edu/%7Ezhiruz/pdfs/sabre-osdi2024.pdf)
- KSM was built to fit more VMs into physical memory by merging identical pages; savings are not guaranteed and per-page metadata can cancel gains (net = pages_sharing x page size minus rmap_items x rmap size). [Linux kernel KSM docs](https://docs.kernel.org/6.3/admin-guide/mm/ksm.html)
- Firecracker v1.13.0 added virtio-mem memory hotplug. [Firecracker CHANGELOG](https://raw.githubusercontent.com/firecracker-microvm/firecracker/main/CHANGELOG.md)
- CVE-2026-122192 (2026-11-04): Firecracker v0.23.0 through v1.16.1, VMs "restored from a snapshot using the File memory backend with a balloon or virtio-mem device" let a guest root user read or modify Firecracker process memory; fixed in v1.16.2 / v1.17.0. [AWS Security Bulletin 2026-169](https://aws.amazon.com/security/security-bulletins/2026-169-aws/)
- Anthropic recommends screen sizes of 1024x768 or 1280x720 for desktop tasks, 1280x800 or 1366x768 for web apps, and avoiding anything above 1920x1080. [Claude computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- Manus sessions run "for hours in persistent sessions", some tasks take dozens of minutes, and paid users can keep sandbox data up to 14 days with pause/resume. [E2B blog: Manus](https://e2b.dev/blog/how-manus-uses-e2b-to-provide-agents-with-virtual-computers)

### Inferences
- Density estimate for a 64-core (128-thread)/256 GB host, leaving about 16 GB for host and VMM overhead: 240 GB / 4 GiB = about 60 desktops; / 3 GiB = about 80; / 2 GiB = about 120. CPU-wise, with 2 vCPU per desktop and a 4:1 overcommit (reasonable when each agent step spends seconds waiting on an LLM), 128 threads support about 256 desktops, so RAM is the limiter by 2x to 4x.
- Memory overcommit is the main lever to break the RAM limit: boot every desktop from one snapshotted "golden" image (shared read-only pages via private file mapping), add KSM for identical pages, and reclaim idle memory with balloon or virtio-mem. Plausible gains are large for identical images, but browsers quickly dirty their heaps, so savings shrink over a session; and the Nov 2026 CVE shows the snapshot plus balloon/virtio-mem path is a live security surface.
- KSM across tenants is also a known side-channel concern (memory deduplication timing attacks), so cross-tenant KSM is usually disabled in multi-tenant clouds; this is general security knowledge not sourced in this research.
- Screenshot frequency: one screenshot per agent step (every few seconds) is a negligible CPU cost (one framebuffer read plus PNG/JPEG encode). Continuous live streaming at 10 to 30 fps with software encoding (no GPU) is a sustained per-desktop CPU cost and can become the largest CPU consumer on an otherwise idle desktop host. Damage-based protocols (VNC) send almost nothing when the screen is static, which agent desktops usually are.
- Pause/resume (snapshot to disk) of idle desktops matters more for economics than raw density, because agent sessions can span hours with long idle stretches (waiting for human confirmation, CAPTCHAs, credentials).

### Gaps
- No primary benchmark found for RAM per full Linux desktop (Xvfb + XFCE + Chromium with N tabs) in a microVM, or for KSM/balloon savings on such desktops.
- No measured CPU cost per screenshot or per fps of software-encoded streaming from Xvfb found; the inferences above are qualitative.

## 5. Computer-use API surface and MCP

### Takeaway
All three major vendors now converge on a similar action vocabulary (screenshot, click variants, drag, move, scroll, type, key/hotkey, wait, plus zoom for Anthropic and navigate for Gemini browser) but differ on coordinate systems (Anthropic and OpenAI use screen pixels with scaling rules; Gemini uses a normalized 1000x1000 grid), image size limits, and safety protocols. Anthropic's newest models (5.x) only accept a new `computer_toolset_20260801` toolset, so an MCP server must translate between vendor schemas. MCP itself changed significantly in the 2026-07-28 spec (stateless, no sessions, explicit handles, tasks moved to an extension), which fits a VM-lifecycle server well, and MCP Apps (Jan 2026) gives a standard way to embed a live-monitoring UI.

- 2025-11-25 introduced experimental Tasks (call-now, fetch-later with `tasks/get` polling). [MCP spec 2025-11-25 tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)

### Inferences
- An MCP server for this product needs a vendor-neutral action schema plus adapters: pixel coordinates with explicit scale factors for Anthropic/OpenAI, normalized 0 to 999 coordinates for Gemini, and screenshots sized to each model's limits (Anthropic's toolset rejects oversized images instead of resizing).
- The 2026-07-28 stateless MCP model maps naturally to `create_machine -> machine_id` handles; long operations (boot, snapshot, restore) should use the tasks extension or return immediately with a handle plus a `get_status` tool, since a dropped stream now loses the in-flight request.
- Returning a base64 screenshot in every tool result is expensive in tokens (1,000 to 1,800 tokens each for Claude) and in MCP payload size; a `resource_link` to a screenshot URL plus an on-demand image is a cheaper default for monitoring-oriented calls.
- MCP Apps (`ui://`) is the standard path to put a live desktop view or fleet dashboard inside Claude/ChatGPT-style hosts, but it depends on host support and sandboxed iframes, so a standalone web dashboard is still needed.
- Lifecycle MCP servers exist (E2B, Daytona), and local desktop-control MCP servers exist, but the research did not find an open, self-hostable server that combines microVM lifecycle, GUI desktop control and fleet-wide live monitoring in one; this appears to be the gap.

- The `computer_20241022` version status and the full action table for `computer_20250124`/`computer_20251124` were truncated in the fetch.

- Cua's own MCP server tool list was not found.

## 6. Security

### Takeaway
MicroVMs are materially stronger than containers, but 2026 showed real escapes: a host-kernel virtio-net/TAP bug (PwnEscape) let a Firecracker guest reach host root on self-managed KVM hosts, and two Firecracker VMM CVEs (one in the PCI transport, one in snapshot plus balloon/virtio-mem) were disclosed, one credited to Anthropic. Running a GUI fleet means agents browse untrusted content with root inside the guest, so the host kernel patch cadence, jailer, seccomp, egress control and credential handling are first-order product features. Public free desktops attract crypto-mining, botnets and phishing, which pushed Heroku, Koyeb and Fly.io to remove or gate free tiers.

### Cited Findings
- PwnEscape (disclosed mid-Oct 2026, reported Nov 9): a bug in the host kernel's IPv4 code on the virtio-net/TAP path leaks 32 bytes of host memory per crafted packet; chained to overwrite a vCPU thread's saved instruction pointer and run code as root on the host. Tested on Firecracker v1.16.1 without the jailer (running as root). Found during Vercel's US$1 million sandbox security challenge, using GPT-5.6 Sol in an experimental harness at under US$700 in tokens. Host kernels 4.4 through 6.18 affected; AWS EC2, Lambda and Fargate were not affected; fix requires patching and rebooting the host kernel. CVE ID given as CVE-2026-99999 looks like a placeholder; scores 9.3 (kernel CNA) vs 8.8 (Red Hat, Amazon, SUSE). [iTnews, 2026-11-09](https://www.itnews.com.au/news/researchers-turn-pwnescape-linux-flaw-into-firecracker-breakout-630201)
- CVE-2026-122192 (2026-11-04): guest root can read or modify Firecracker process memory for snapshot-restored VMs using the File memory backend with balloon or virtio-mem; v0.23.0 to v1.16.1 affected; fixed v1.16.2 / v1.17.0; Coinspect also demonstrated a two-stage escape combining it with a seccomp bypass. [AWS Security Bulletin 2026-169](https://aws.amazon.com/security/security-bulletins/2026-169-aws/); [Feedly CVE summary](https://feedly.com/cve/CVE-2026-122192)
- CVE-2026-5747 (Apr 2026): out-of-bounds write in Firecracker's virtio PCI transport (1.13.0 to 1.14.3 and 1.15.0) lets a guest root crash the VMM; fixed 1.14.4/1.15.1; credited to Anthropic. [NVD CVE-2026-5747](https://nvd.nist.gov/vuln/detail/CVE-2026-5747); [AWS Security Bulletin 2026-015](https://aws.amazon.com/security/security-bulletins/2026-015-aws)
- CVE-2026-1386 (Jan 2026): Firecracker jailer symlink issue allowing arbitrary host file overwrite under certain circumstances. [AWS Security Bulletin 2026-003](https://aws.amazon.com/security/security-bulletins/2026-003-AWS)
- Anthropic's computer-use guidance: use a dedicated VM or container with minimal privileges, avoid giving the model sensitive data such as logins, limit internet access to an allowlist of domains, and require human confirmation for consequential actions. [Claude computer use tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- Gemini exposes safety policy categories (financial transactions, account creation, communication tools, legal terms) that trigger `require_confirmation`. [Google AI Studio computer use docs](https://aistudio.google.com/docs/computer-use)
- Chromium warns SwiftShader WebGL is "not intended for running untrusted content" because JIT-ed code runs in the GPU process. [Chromium SwiftShader doc](https://chromium.googlesource.com/chromium/src/+/798e59c5275d4131797e8ea2e96e6c6000256b58/docs/gpu/swiftshader.md)
- Abuse: Modal moved from metadata heuristics to syscall-based runtime detection of crypto miners (e.g., processes connecting to known mining pools on unusual ports), with zero false positives reported (Jun 2024). [Modal blog: catching cryptominers](https://modal.com/blog/catching-cryptominers). Fly.io staff cite crypto miners, botnets and phishing sites as abuse that hurts margins. [Fly.io community](https://community.fly.io/t/free-tier-is-dead/20651/6). Heroku ended free plans in 2022 citing fraud and abuse. [TechCrunch, 2022-08-25](https://techcrunch.com/2022/08/25/heroku-announces-plans-to-eliminate-free-plans-blaming-fraud-and-abuse). Koyeb required a payment method for everyone in Dec 2022 due to an "exponential surge of abuse". [Koyeb blog](https://koyeb.com/blog/sustaining-free-compute-in-a-hostile-environment). Crypto-mining gangs abuse free cloud/CI platforms broadly. [The Record](https://therecord.media/crypto-mining-gangs-are-running-amok-on-free-cloud-computing-platforms/)
- E2B's free Hobby tier is a one-time $100 usage credit (other sources cite concurrency/runtime caps; conflicting). [E2B pricing](https://e2b.dev/docs/pricing)
- MCP 2026-07-28: servers MUST validate inputs, implement access controls, rate limit invocations and sanitize outputs; handles for unauthenticated servers are bearer tokens and need high entropy and bounded lifetime. [MCP spec 2026-07-28, Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### Inferences
- Isolation ranking for untrusted agent desktops: plain containers (shared host kernel, weakest) < gVisor (user-space kernel) < microVM with jailer + seccomp (Firecracker/Cloud Hypervisor) < microVM on dedicated host per tenant. Even microVMs depend on the host kernel's virtio-net/TAP path, as PwnEscape showed; patching host kernels quickly (with reboot or live migration) is mandatory operational capacity.
- Memory-overcommit features (snapshot + balloon/virtio-mem) and newer transports (PCI) are where recent VMM bugs landed; a "lightweight" platform should pin to patched Firecracker (>= 1.16.2 or 1.17.0) and treat those features as opt-in.
- Network egress control is essential both for safety (prompt-injection exfiltration) and abuse (mining pools, spam, credential stuffing). Default-deny egress with per-machine allowlists, an SMTP block, and rate limits make a hosted desktop far less attractive to abusers.
- Credential injection should avoid putting secrets in the guest at all when possible (e.g., a host-side proxy that injects auth headers or a vault that types credentials into a specific field after human confirmation); otherwise the screenshot stream and recordings leak them.
- A public hosted version needs card verification or prepaid credits before any GUI desktop is granted, plus runtime detection (CPU pinned at 100%, mining-pool DNS/ports), consistent with what Heroku, Koyeb, Fly.io and Modal ended up doing.

### Gaps
- No public anti-abuse policy details were found for E2B, Browserbase or Daytona desktops specifically.
- No data found on how often hosted browser/desktop sandboxes are used for ad fraud or account farming, though Gemini's safety categories suggest vendors anticipate it.

## 7. Observability at scale

### Takeaway
Streaming every desktop continuously is the hidden cost driver: at typical WebRTC/VNC bitrates, cloud egress for one watched stream can cost as much as or more than the compute for the desktop itself on AWS. The practical design is low-rate thumbnails for the fleet grid, full-rate streams only for the desktop a human is focused on, and recordings stored as screenshot-plus-action logs (which the agent loop already produces) rather than continuous video. OpenTelemetry GenAI agent conventions exist (still "Development" status) and MCP now standardizes trace-context propagation.

### Cited Findings
- A 2021 study including noVNC found its WebRTC-based implementation performed best and used at most about 3 Mbps. [NYCU / ACM TOMM 2021](https://people.cs.nycu.edu.tw/~chuang/pubs/pdf/2021tomm.pdf)
- About 10 Mbps for 1080p is described as more than acceptable for remote desktop video; WebRTC supports hardware-accelerated H.264/VP8/VP9/AV1 encoding. [e-INFRA CZ blog](https://blog.e-infra.cz/blog/witcher-in-browser/). Planning guide: 1080p30 needs 6 to 10 Mbps upload, 1080p60 12 to 20 Mbps (not protocol specific). [Remote desktop bandwidth guide](https://dev.to/hle0029/how-much-upload-bandwidth-does-remote-desktop-game-streaming-actually-need-3pa6)
- Below about 2 Mbps, WebRTC (Selkies) vs VNC quality trade-offs appear at 1080p; the noVNC HTML5 client lacks TurboVNC-like optimizations. [Selkies issue 152](https://www.github.com/selkies-project/selkies-gstreamer/issues/152); [kasmtech/noVNC](https://github.com/kasmtech/novnc)
- S3 Standard storage is $0.023/GB-month (first 50 TB, us-east-1); internet egress about $0.09/GB after the first 100 GB/month. (secondary) [CloudZero](https://www.cloudzero.com/blog/s3-pricing); [Upstash S3 pricing 2026](https://upstash.com/blog/aws-s3-pricing-explained-2026)
- OpenTelemetry GenAI agent spans (`create_agent`, `invoke_agent {agent_name}`, `execute_tool {tool_name}`) are in Development status; the conventions moved to a separate semantic-conventions-genai repository on 2026-06-12 (v1.42.0); MCP tool calls produce the same `execute_tool` span shape as direct tool calls. [OpenTelemetry GenAI agent spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-agent-spans/index.md); [Dash0, updated 2026-09-14](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained); [Honeycomb agents docs](https://docs.honeycomb.io/send-data/agents)
- MCP 2026-07-28 documents propagating `traceparent`, `tracestate`, `baggage` in `_meta`, and deprecates the MCP Logging feature in favor of stderr or OpenTelemetry. [MCP changelog](https://modelcontextprotocol.io/specification/latest/changelog)

### Inferences
- Egress math (AWS internet egress at $0.09/GB): 2 Mbps continuous = 0.9 GB/hour = about $0.08/hour per viewed stream; 6 Mbps (1080p30) = 2.7 GB/hour = about $0.24/hour. That exceeds the roughly $0.05 to $0.10/hour compute cost of a desktop on AWS metal (section 8). On Hetzner, generous included traffic largely removes this cost (not verified here).
- Thumbnail grid math: a small JPEG (assume about 30 KB at 320x200) every 2 seconds per machine is about 54 MB/hour per machine; 100 machines is about 5.4 GB/hour of fan-out to one dashboard viewer, so thumbnails should be fetched only for visible tiles and paused on hidden tabs.
- Recording storage math: screenshot + action log at one 1280x800 JPEG (assume about 150 KB) per agent step every 5 seconds = about 108 MB per session-hour, about $0.0025 per month per stored session-hour on S3 Standard. Low-motion H.264 at 0.5 to 1 Mbps = 225 to 450 MB/hour, about $0.005 to $0.01 per month per stored hour. Storage is cheap either way; encoding CPU (no GPU in microVMs) and egress are the real costs, which favors screenshot logs since the agent already captures them.
- Model-side cost dwarfs infra: at 1,000 to 1,800 tokens per Claude screenshot and one screenshot every 5 seconds, a session-hour sends roughly 0.7 to 1.3 M new image tokens (before context accumulation), which at any plausible per-million-token price is dollars per hour vs cents per hour of desktop compute.
- Use OTel spans per agent step (`execute_tool` for each computer action, with machine_id and screenshot resource link as attributes) so recordings and traces join on trace IDs; this works across MCP clients because MCP now carries `traceparent` in `_meta`.

### Gaps
- No controlled benchmark of noVNC vs WebRTC (e.g., Selkies, Neko, KasmVNC) bandwidth and server CPU at 1280x800 for mostly-static agent desktops was found.
- Current Hetzner/OVH included-traffic allowances for 2026 dedicated servers were not verified.
- Current per-token pricing for Claude 5.5, GPT-6.x and Gemini 4 models was not researched.

## 8. Economics: provider cost per desktop-hour vs vendor prices

### Takeaway
Raw compute for a 2 vCPU / 4 GiB Linux desktop costs a provider roughly $0.05 to $0.10 per hour on AWS bare metal at full occupancy (about $0.025 on spot) and well under 1 cent per hour on Hetzner bare metal, while vendors charge about $0.10 to $0.17 per hour for equivalent sandboxes or browsers. At 2 GiB with 2:1 CPU overcommit, about 180 desktops, about $0.048/hour. Break-even vs a $0.166/hour price is about 57% average occupancy at 4 GiB, or about 29% at 2 GiB, before egress, storage, snapshots and staff.
- Hetzner AX162-R at EUR 242.30/month is about EUR 0.33/hour for the whole host; assuming about 256 GB RAM (spec not verified here) and about 60 desktops at 4 GiB, that is about EUR 0.0055 per desktop-hour, roughly 15x to 30x cheaper than AWS on-demand per desktop, at the cost of no elasticity (monthly commitments, setup fees, manual capacity planning).
- For an open, self-hostable product, the economic pitch is strongest for "bring your own bare metal or Hetzner box"; a hosted SaaS has to price above about $0.10/hour (AWS) or carry idle bare-metal capacity, and must budget for abuse losses that forced competitors to gate free tiers.
- Hosted macOS is economically and legally unattractive: about $21 minimum per 24-hour Mac host allocation for at most 2 macOS VMs, used only for development/testing purposes.
- LLM token spend per session-hour (section 7) is likely 10x to 100x the infra cost, so customers are less price-sensitive on desktop-hours than on reliability, latency, and observability, which argues for competing on features (fast snapshot/resume, monitoring, MCP integration) rather than on the lowest per-hour price.

### Gaps
- No primary 2026 pricing for desktop-specific (GUI) sandboxes from E2B, Daytona, Scrapybara or Cua's successor offering was found.
- AWS C8i bare-metal and nested-capable instance prices were not collected.
- No public data on actual occupancy/utilization rates for agent sandbox fleets, which is the key break-even variable.
